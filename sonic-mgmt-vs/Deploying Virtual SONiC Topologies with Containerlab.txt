Deploying Virtual SONiC-Mgmt Topologies with Containerlab
Abstract:
Current SONiC management testbeds, while supporting both VMs and containers, rely on complex Ansible playbooks and scripts for orchestration. This imperative approach can be cumbersome to maintain and slow to deploy. Our talk introduces a paradigm shift: moving to a streamlined, declarative model using Containerlab, with utilizing a containerized SONiC, built with vrnetlab, as the Device Under Test (DUT).
This session will present a case study of a t1-small topology where, for the first time, a lightweight SONiC container serves as the DUT alongside cEOS neighbors and a PTF traffic generator. We will detail our solution for clean management access to this containerized DUT using the "sidecar" pattern—a separate Debian container sharing the DUT's network namespace for running agents and scripts, leaving the DUT environment pristine.
Attendees will see a direct comparison between the legacy Ansible automation and the new Containerlab-centric workflow. We will demonstrate how Containerlab's declarative topology files simplify network definitions, while orchestrating tasks beyond its scope, like OVS bridge creation, are managed efficiently through pre and post-deployment wrapper scripts.
Join us to explore the benefits, and practical considerations of deploying a fully containerized SONiC testbed.
1. Objective
The goal is to migrate our virtual SONiC management and testing deployments from an Ansible and script-based framework to a more streamlined and declarative model using Containerlab (clab). This document outlines the strategy for creating a t1-small virtual topology, which integrates a containerized SONiC DUT, cEOS routers, a PTF traffic generator, and the necessary network infrastructure.

2. Scope: Virtual vs. Physical Topologies
Presently, our environment includes both virtual and physical testbeds. This initiative will begin by focusing exclusively on virtual topology deployments.
Automating physical testbeds presents a greater challenge, as it involves creating and managing host-level network configurations (like VLAN interfaces) that connect containers to physical server interfaces. By starting with the virtual t1-small topology, we can prove the viability of this model in a self-contained environment before addressing the complexities of physical hardware integration.
3. Core Concepts & Strategy
  

We are transitioning from using a full SONiC Virtual Machine (VM) to a more lightweight, [a]container-based alternative built with vrnetlab. This approach significantly speeds up deployment and reduces resource consumption. Containerlab will serve as the orchestrator for defining and linking all the containerized components of our lab.
We can also replace `setup-container.sh` with clab topology
Key Implementation Points:
* Containerized SONiC DUT: The SONiC VM is replaced by a container. This container acts as our primary Device Under Test (DUT).
* Sidecar Containers for Management: To keep the DUT container clean and realistic, we will use the "sidecar" pattern. A separate Debian container will share the network namespace of the SONiC DUT. This allows us to run management tools, scripts, and agents in the sidecar while the DUT's environment remains pristine. This is the recommended approach and answers the question of how to manage a container-based DUT.
* OVS Bridge Pre-configuration: Containerlab does not manage the lifecycle of Open vSwitch (OVS) bridges. All required OVS bridges must be created on the host system before deploying the lab. A pre-deployment script is the ideal way to handle this setup.
* Workflow Automation: The entire lab lifecycle will be managed by scripts that wrap the Containerlab commands. This includes:
   * Pre-Deployment: Scripts to create OVS bridges and prepare configuration files.
   * Post-Deployment: Scripts to run initial device configurations or tests.

The following Containerlab topology file defines the t1-small lab. It is structured to be readable and clearly separates different types of components.

     # Topology Name: t1-small
# Description: A virtual lab for SONiC testing featuring a containerized SONiC DUT,
#              cEOS neighbors, a PTF tester, and a dedicated management container.
name: t1-small


topology:
  nodes:
    # 1. Host Network Infrastructure (Must be created manually before deploy)
    # Containerlab can connect to existing host bridges but will not create them.
    br-VM0100-0:
      kind: ovs-bridge
    br-VM0101-0:
      kind: ovs-bridge
    br-b-vms6-1:
      kind: ovs-bridge
    br1:
      kind: ovs-bridge


    # 2. Core Network Emulation Nodes
    sonic-dut:
      kind: vr-sonic # Using vrnetlab's custom kind for SONiC
      image: vrnetlab/sonic-vs:latest # Using a containerized SONiC image
      # The 'vr-sonic' kind is a conceptual example; you would use 'linux' or a custom kind.


    ptf:
      kind: linux
      image: container-registry.sw.internal.nexthop.ai:443/docker-ptf:latest-20250620


    sonic-mgmt:
      kind: linux
      image: sonicdev-microsoft.azurecr.io:443/docker-sonic-mgmt:latest
      # This container connects to the default docker bridge for external access.


    # 3. Arista cEOS Router Nodes
    t0:
      kind: ceos
      image: ceosimage:4.32.5M-1
      binds:
        - ../../config/t1_neighbor/frr-2.conf:/etc/frr/frr.conf


    t2:
      kind: ceos
      image: ceosimage:4.32.5M-1
      binds:
        - ../../config/t1_neighbor/frr-1.conf:/etc/frr/frr.conf


    # 4. Sidecar Management Containers
    # These share the network namespace of their target node, providing a clean
    # way to manage the node without installing tools on it directly.
    t0-sidecar:
      kind: linux
      image: container-registry.sw.internal.nexthop.ai:443/debian:bookworm
      network-mode: container:clab-t1-small-t0 # Shares the network stack of 't0'


    t2-sidecar:
      kind: linux
      image: container-registry.sw.internal.nexthop.ai:443/debian:bookworm
      network-mode: container:clab-t1-small-t2 # Shares the network stack of 't2'


  links:
    # --- DATA VETH PAIRS ---
    # Connects cEOS and SONiC data ports to their respective OVS bridges.
    - endpoints: ["t0:eth1", "br-VM0100-0:VM0100-t0"]
    - endpoints: ["t2:eth1", "br-VM0101-0:VM0101-t0"]
    - endpoints: ["sonic-dut:eth1", "br-VM0100-0:vlab-01-1"]
    - endpoints: ["sonic-dut:eth2", "br-VM0101-0:vlab-01-2"]


    # --- PTF INJECT VETH PAIRS ---
    # Connects the PTF container to the data bridges for traffic injection/reception.
    - endpoints: ["ptf:eth0", "br-VM0100-0:inje-vms6-1-0"]
    - endpoints: ["ptf:eth1", "br-VM0101-0:inje-vms6-1-1"]


    # --- MANAGEMENT VETH PAIRS ---
    # Connects all node management interfaces to a common 'br1' management bridge.
    - endpoints: ["sonic-dut:eth0", "br1:sonic-dut-mgmt"]
    - endpoints: ["t0:eth0", "br1:VM0100-m"]
    - endpoints: ["t2:eth0", "br1:VM0101-m"]
    - endpoints: ["ptf:eth2", "br1:ptf-vms6-1-m"]


    # --- BACKPLANE VETH PAIRS ---
    # Connects all nodes to a common backplane bridge.
    - endpoints: ["sonic-dut:eth4", "br-b-vms6-1:sonic-dut-back"]
    - endpoints: ["t0:eth5", "br-b-vms6-1:VM0100-back"]

5. Proposed Workflow
1. Prerequisites: Ensure Docker, Containerlab, and Open vSwitch are installed on the host machine.
2. Pre-Deployment:
   * Create a bash script (setup_infra.sh) to automatically create the required OVS bridges: br-VM0100-0, br-VM0101-0, br-b-vms6-1, and br1.
   * Ensure all necessary container images are available locally or in the specified registries.
   * Place all configuration files (e.g., frr.conf) in the correct paths referenced by the binds mounts.
3. Deployment:
   * Execute the setup script: bash setup_infra.sh.
   * Deploy the lab using the topology file: sudo clab deploy -t t1-small.clab.yml.
4. Post-Deployment:
   * Run any post-deployment scripts or Ansible playbooks, likely targeting the sonic-mgmt container, to configure the devices in the lab.
5. Teardown:
   * Destroy the lab containers and links: sudo clab destroy -t t1-small.clab.yml --cleanup.
   * Run a cleanup script (teardown_infra.sh) to delete the OVS bridges.
6. Final Thoughts
It is certainly feasible to deploy SONiC management topologies—at least the smaller-scale ones—using Containerlab. The existing automation, a combination of Ansible playbooks, shell scripts, and Python, performs many orchestration tasks that fall outside the scope of Containerlab's core responsibilities.
Therefore, clab cannot be a direct, drop-in replacement for the entire toolchain. We must shift logic that Containerlab cannot handle (such as the creation of OVS bridges) into pre- and post-deployment wrapper scripts. While this makes the topology definition itself cleaner, the surrounding automation scripts will inevitably grow in complexity as they absorb the responsibilities of the old playbooks.
This leads to the main question: is the time and effort required for this migration worth it? While the answer depends on long-term goals, this is an interesting and promising idea to explore, and starting with a proof-of-concept for the t1-small topology is an excellent first step.
